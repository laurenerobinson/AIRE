## Completed behavior

- **Binary Library / Upload:** a file selection uploads raw bytes and validates
  actual ELF/PE headers and file-backed ranges. Filename, format, architecture,
  size and full SHA-256 appear before **Start static analysis** is enabled.
  Extensions are not trusted. Empty, nonbinary, oversized and truncated files
  are rejected; the limit is 32 MiB.
- Upload storage uses a hash directory, sanitized basename and nonexecutable
  permissions. Client directory components are discarded; symlink escapes are rejected.
  Indexing checks SHA-256 before/after work; original binary bytes are retained.
- Jobs show queued/running/completed/failed status, timestamped phases,
  measured processing/queue/total times and cache status. Warnings and timings
  persist in `demo_artifacts/oct22/uploads/*.job.json`; Ghidra logs are in
  `index-worker.log`. A failed analysis does not replace a prior snapshot.
- One serialized queue talks to one persistent Python child process. Indexing,
  JVM initialization and SQLite writing stay on that child's main thread.
  Later requests reuse its process/JVM. GUI request threads investigate through
  read-only connections and exchange progress values, never Java objects.
- The library reads `tests/fixtures/external/manifest.json` and explicit local
  demo binary paths. It shows ELF/PE, architecture, availability and cache
  status, and opens investigations without uploading again. “Cached” requires
  matching SHA-256, complete indexing options, extraction/reference versions,
  PyGhidra version and configured Ghidra version/revision. Older snapshots are
  labeled indexed but needing refresh. No GitHub synchronization was added.
- Initial metadata and function browsing defer overview evidence and security
  evaluation. Expensive views load on demand, using the existing bounded tool
  cache and provenance. Function browsing supports paging and exact addresses.
- **Assembly**, **Cross-references**, **Thunk / Jump target** and **Arithmetic
  evidence** expose existing stored tools. The arithmetic panel explains local
  integer/scalar floating-point multiplication with exact instruction addresses
  and function source IDs. It does not claim whole-function equivalence or
  recovery of original source parameter types.

Source and ground truth are instructor comparison material only. The indexer
receives binary paths; model prompts receive binary-derived SQLite evidence.
Original C/C++ and ground-truth text are not added to analysis/model inputs.
Direct CALLs, indirect references and JMP/thunk bindings remain distinct.

## Professor evidence and explanation

Addresses are Ghidra virtual addresses for the hash-pinned PE. Full tool outputs,
source IDs, references and relationships are in
[DEMO_2026-10-22_verification.json](DEMO_2026-10-22_verification.json).
Function source IDs in `functions` are `<binary SHA-256>:<address>`;
`binary_references` rows retain separate IDs and source/target addresses.

| Source comparison | Stored function | Exact binary evidence | Supported behavior |
|---|---|---|---|
| `int square(int x)` | `FUN_00412620` at `00412620` | `0041267f: MOV EAX,[EBP+0x8]`; `00412682: IMUL EAX,[EBP+0x8]` | Integer argument multiplied by itself; EAX carries the result. Source `square(7)` corresponds arithmetically to 49. |
| `double square(double y)` | `FUN_004126c0` at `004126c0` | `00412727: MOVSD XMM0,[EBP+0x8]`; `0041272c: MULSD XMM0,[EBP+0x8]`; store at `00412731`; `FLD` at `00412739` | Scalar double multiplication, transferred to the x87 return path. Source 7.5 squared is 56.25. This is neither square root nor a sum of two source arguments. |

The decompiler reports a `float10` return and two `undefined4` parameters for
the floating body. Those are ABI/type-recovery artifacts. Source comparison,
the 64-bit operations and caller argument construction support the demonstrated
mapping; do not present the recovered signature as the original declaration.
49 and 56.25 are mathematical expectations, not observed execution output.

The complete PE is not an exact reproduced build of the supplied source:
its main also references `PAUSE` and calls through the `system` import at
`0041285c`, which is absent from `FunctionOverloading.cpp`. The overload mapping
above is corroborated by instructions, constants and strings; it does not
establish whole-file source equivalence. That call was never executed.

Caller `FUN_00412790` pushes 7 at `004127b8`, then CALLs `00411028` at
`004127ba`. That thunk JMPs to `00412620`. The floating case loads the eight-byte
constant at `00419b70` at `004127f5`, places it on the stack at `004127fd`, then
CALLs `004110cd` at `00412802`; that thunk JMPs to `004126c0`. Stored read bytes
decode to 7.5. `00411325` is a separate entry thunk to `00412790`.

The direct call graph targets the thunks. Empty direct callers on the bodies
are expected: JMP bindings are not CALL edges. Use **Thunk / Jump target** to
resolve them. Exact function-owned strings further corroborate identification:

- `00412653` → `00419b38`: `square of integer `.
- `004126fc` → `00419b50`: `square of double `.

Select each address in **Functions**, then inspect **Arithmetic evidence**,
**Assembly**, **Cross-references**, **Call Graph** and **Decompiled View**.
