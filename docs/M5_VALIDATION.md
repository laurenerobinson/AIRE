## Configurable context and targeted live validation — 2026-09-22/23

### Minimal code and configuration change

The only production change is in `aire-server/src/aire/ai/ollama_client.py`.
`OllamaClient(..., num_ctx=None)` resolves the keyword-only argument, then
`AIRE_OLLAMA_NUM_CTX`, then the preserved default **32768**. Environment input
must be positive ASCII decimal digits; malformed/empty strings, zero and negative
values raise a clear ValueError without fallback. Explicit arguments must be
positive Python integers, excluding bool, float and string, and override the
environment. The resolved integer is sent as `options.num_ctx`.

Host/model precedence, temperature, seed 0, `num_predict=2048`, socket-timeout
defaults, response limits, JSON/citation validation, fact reconstruction, prompt
instructions, retry policy and local-only-default networking are unchanged.
No tokenizer or new runtime dependency was added. M1–M4 were not changed.

Seven new pure tests cover the default, environment-to-request serialization,
malformed/zero/negative environment input, explicit precedence and invalid
explicit types. The existing request test now also checks the unchanged output
cap and default context. Host/model/temperature behavior is checked together with
the override. The pure run passed **149 tests**, with eight opt-in integration
cases skipped.

`test_chat_integration.py` gained only an optional test resource setting:
`AIRE_CHAT_TEST_CONTEXT_CHARS`. It affects live requests only; their default is
still 24,000 characters. All original assertions remain unchanged, including
selection of both direct-callee facts, citation provenance, confidence,
truncation, zero database writes and fixture hashes. Static/fake cases retain
their original budgets. Normal requests use `ChatRequest.max_total_context_chars`.

## 7–8. Request and response

ChatRequest: binary ID, question, optional exact target and target_by, depth,
function/artifact/edge/context-character caps, assembly/decompile flags. Defaults:
depth 1, 8 functions, 12 artifacts, 20 edges, 24000 evidence characters. All
request dimensions have finite validation bounds. No target means an explicitly
non-semantic root/connectivity overview; explicit target uses M4 unchanged.

ChatResponse: question, binary ID, target, cited advisory summary, deterministic
facts, cited interpretations/confidence, uncertainties, provenance/citations,
EvidenceBundle, context_truncations/context_truncated, selection policy, model,
attempts, timing, sizes, and opt-in raw_response. It is JSON serializable.

## 9–10. Prompt and injection defenses

A constant separate system instruction limits reasoning to supplied evidence.
The question and binary-derived strings/names/comments/code are JSON-escaped
untrusted data. The prompt includes selection policy, evidence blocks, truncation
summary and strict schema. Binary instructions cannot become system-role text.
The retry does not echo malformed model output. There are no model tools or
execution hooks. Terminal control characters are escaped. Prompt defenses do
not prove a model will obey; strict fact reconstruction protects the fact channel.

## 11–12. Citations and facts versus interpretation

Stable aliases use category plus 16 hex SHA-256 characters, mapped back to full
M4 source identity/provenance. Only evidence blocks actually sent to the model
receive valid aliases; omitted items cannot be cited. Collisions fail closed.

The model returns `fact_ids`, not arbitrary fact prose. The application renders
precomputed statements about actual bundle records and callsites. Model summary
and interpretation remain advisory even with valid citations; existence checks
are not semantic entailment checks. Interpretation confidence must be low/medium/high.
No model interpretation is saved to SQLite or Ghidra.

## 13–14. Truncation and validation/retry

M4 truncations and additional prompt-block omissions are exposed to both model
and analyst. Deterministic uncertainty notes disclose static-only evidence,
bounded context, disabled code types and character-versus-token limitations.

Parsing requires strict JSON with exact fields, bounded lists/nonblank strings,
nonempty valid claim citations and valid confidence. Duplicate keys/IDs,
nonfinite numbers, nonexistent citations and malformed nested values fail.
One format correction is permitted; a second failure raises structured ChatError.
Transport/evidence-resolution failures do not invoke that retry. Raw replies are
retained only on explicit debug requests and are never automatically logged.
